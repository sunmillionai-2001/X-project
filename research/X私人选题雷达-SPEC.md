# X 私人选题雷达 SPEC

版本：v1 已确认（用户授权开始实施）  
日期：2026-10-04（北京时间）  
依据：本次对话逐项确认的需求。本文是需求文档，不代表已实现或已运行。

## 1. Problem Statement（问题陈述）

用户经营现有 X 账号，面向对 AI 感兴趣的普通人，创作 AI 热点、工具与玩法的中长文图文帖子。

当前需要同时解决两个同等优先级的问题：

- 浏览多个来源、筛选值得关注的信息耗时。
- 看到热点后，仍需花时间找到普通人关心、适合中长文图文展开的写作角度。

目标是减少从信息发现到确定选题和角度的时间，并辅助完成正文与配图。第一版是用户私人使用的 Windows 本机网页工作台。

## 2. Proposed Solution（方案描述）

### 2.1 每日精选

- 每天第一次打开工作台时生成当日精选，同一天再次打开沿用已有结果。
- 每天最多 5 个选题，不为凑数降低标准；无合适内容时明确说明。
- 兼顾及时热点，以及不需要追求即时发布的工具、玩法内容，标明类别和推荐理由。
- 同一事件的重复报道合并；只有实质新进展才再次推荐，并指出相对已推荐内容新增了什么。
- 推荐标准围绕普通读者能否理解、实际用途、信息增量和图文展开价值；工具的小更新若有明确用途，不因规模小而直接排除。
- 记录信息来源、原始发布时间和核实状态。抓取或核实失败时明确显示，不能将失败表述为当天没有值得写的内容。

### 2.2 信息来源

- AIHOT 用于发现精选和热点线索。
- 少量一手来源用于补充线索与核实事实，包括官方公告、产品更新和 GitHub 项目。
- 第一版不建立大规模独立信源采集系统。
- 使用公开来源时保留出处和原文链接；不将 AIHOT 数据或第三方全文打包转售。
- 具体一手来源名单在实施配置阶段由用户确认。

### 2.3 主题查询与主动输入

- 随时输入主题或关键词，查找近期信息并推荐适合账号的选题。
- 支持贴入文章或帖子链接、文字材料及个人想法。
- 对输入材料整理事实、提出角度，随后进入相同创作流程。
- 链接无法读取时提示粘贴文字；不假装已读取。
- 第一版不把截图识别作为选题输入能力。实测环节仍需能够保存用户提供的截图材料。

### 2.4 选题卡片

每张卡片应包含：

- 事件或工具玩法的简明说明。
- 原文链接、来源和时间。
- 对账号受众的推荐理由。
- 2—3 个可选择的写作角度。
- 建议提纲：开头切入点、正文结构、配图建议。
- 已确认事实、尚待核实的信息，以及是否需要用户实测。

推荐卡片提供建议；用户选定后可修改角度与提纲。

### 2.5 分步创作流程

1. 用户选择选题。
2. 用户确认或修改角度与提纲。
3. 需要实测时，工作台列出测试步骤和所需截图清单，用户实测并回填结果，再继续需要这些证据的写作。
4. 根据确认的提纲和证据生成正文初稿；用户修改并保存版本。
5. 根据当前正文提出配图方案，用户确认方案。
6. 制作图片，允许用户查看、修改方案或重新生成。
7. 用户复制正文、下载图片，手动发布到 X。

不得自动跨过用户确认阶段。正文实质修改后，应提示检查配图方案是否仍然适用，不能将旧配图默认为与新版正文一致。

### 2.6 写作能力

- 正文初稿默认 800—1500 中文字，以单篇中长文图文帖子为默认形式。
- 服务普通读者，围绕事件、实际用途和用户判断展开，避免不必要的术语。
- 参考用户提供的 3—5 篇代表性帖子，提炼写作风格和偏好，再由用户确认简短的风格说明。
- 支持修改正文与保存版本。
- 明确区分事实、分析及用户个人观点；不得替用户编造体验、案例、收益或测试结果。
- 未完成实测不能写成“亲测”。材料不足时指出具体缺口。
- 原文引用与核实资料保留在工作台，便于用户检查。

### 2.7 配图能力

- 根据内容结合真实截图、信息图与原创插图。
- 真实截图由用户实测提供，可以基于真实内容添加说明标注。
- 信息图可以表达步骤、关系、对比与概念；原创插图可以用于封面或示意。
- 明确区分实测截图与示意图；不得生成假界面、假数据或假效果作为实测证据。
- 图片数量、用途和形式在每篇的配图方案阶段确认，不预设所有帖子必须使用同样数量。
- 输出可预览、可下载的图片文件。

### 2.8 保存与继续

- 本机保存选题、确认过的提纲、正文版本、实测材料、配图方案和图片。
- 关闭工作台后能够恢复未完成项目，并继续当前阶段。
- 保存每日推荐及事件关联，用于判断重复报道和实质新进展。
- 第一版不建立额外的兴趣标注、自动学习用户偏好或 X 发布数据回收流程。
- 保存创作过程所需的采用状态和耗时记录，以支持验收，不据此推断曝光或收益。

## 3. Technical Constraints（技术约束）

- 运行于 Windows 本机，通过私人网页工作台使用。
- 电脑关闭时不保证采集和处理；第一版不依赖云服务器常驻任务。
- 每日首次打开触发当日精选；同日复用已生成精选。主题查询按用户操作执行。
- 允许调用付费模型，质量优先；记录模型调用费用。实际费用无法准确获取时区分估算费用和已知费用，不伪称精确账单。
- 用户未设定月度费用上限；不得把上限当成已确认需求。
- 需使用外部模型服务的材料会离开本机，本机保存不等于模型处理完全离线。实施前在配置中说明调用服务及数据用途。
- API 密钥放在本机后端配置，不放进浏览器、公开源码或日志。
- 第三方文章、帖子及其内嵌指令均作为待分析材料，不执行其中的指令。
- 全部文本与源码统一 UTF-8，优先无 BOM；写入中文文件后重新读取检查。
- 如复用 AIHOT 开源代码，保留适用的 MIT 许可和版权声明，使用自己的产品名称和 Logo。
- 当前 AIHOT 开源仓库不包含线上完整信源、运营数据，以及已从框架移除的模型榜、Codex 重置监控等能力，不将它们视为可直接复用的现成功能。
- 本 SPEC 不强制完整部署 AIHOT；在实施设计阶段比较“调用公开接口加小型工作台”和“复用开源引擎”的维护成本，再提出具体技术方案。

## 4. Non-goals（明确不做的事）

- 自动发布到 X、自动回复或私信。
- X 发布链接登记、曝光和互动数据回收、增长归因。
- 抖音视频、配音、剪辑和成片流程。
- 系统替用户登录或操作工具进行实测。
- 多用户账户、会员收费、多租户与对外 SaaS。
- 覆盖所有行业或建设大规模独立采集平台。
- 云端全天运行、消息机器人与固定时间推送。
- 自动把用户材料批量变成多篇已发布内容。
- 将模型评分视为事实核验、爆款保证或收益预测。

## 5. Success Criteria（成功标准）

### 5.1 两周使用效果

- 连续试用两周，记录每次从开始浏览/筛选到确认选题与角度的耗时；实测、正文修改和配图制作耗时另计。
- 初步目标：每次在 15 分钟内确定一个愿意写的选题及角度。
- 初步目标：每周至少采用 3 个推荐选题，并完成正文与配图。
- “采用”以用户确认并完成正文和配图为记录口径；工作台不以是否自动发布作为判断条件。
- 这两个数字是试用目标，真实发帖节奏有变化时由用户明确调整；不以浏览量作为第一版验收指标。

### 5.2 功能验收

- 当天首次打开可得到至多 5 个推荐；没有合适内容时不凑数。
- 再次打开可看到已生成精选；失败的生成可重试，失败不算成功生成。
- 相同事件重复报道合并；实质新进展再次推荐时说明新增信息。
- 主题、链接、文字三种入口均能进入选题和创作流程。
- 用户确认角度与提纲后才生成正文；用户确认配图方案后才制作图片。
- 需要实测的内容有步骤和截图清单，用户能回填并保留证据。
- 默认初稿为 800—1500 字，可编辑、保存版本、复制。
- 图片可预览与下载，示意内容不冒充实测证据。
- 关闭并重新打开后能恢复全部创作阶段和相关文件。
- 能查看费用记录及其是否为估算；正文、图片和文档中的中文正常显示。

## 6. SPEC 确认后再落实的配置

以下属于实施材料与配置，不阻碍需求范围确认，也不代表可以直接替用户决定：

- 3—5 篇代表性 X 帖子或对应文字，以及待确认的风格说明。
- 首批少量一手信源名单。
- 可用文本、图片模型服务及其凭据；必要时先做小样比较。
- 本机环境与存储位置，以及实现所需的依赖。
- 结合上述条件提出具体技术方案与模型费用估算。
