# X-agent-skill 接入评估

评估日期：2026-10-08（北京时间）。

上游：[zhuy3075-ui/X-agent-skill](https://github.com/zhuy3075-ui/X-agent-skill)。本次实际读取 `v1.1.0` 对应提交 `98e56b33c08d6cc1e7cfa49bbda3a6fd5465a6de`，不依据宣传文字判断已实现能力。源码评估副本保存在被 Git 排除的 `.research/` 下。

## 结论

可以复用和二次开发。更适合成为工作台的可选采集与研究服务，重点补上可见评论、正文版本、互动快照和研究资料沉淀。现有 DeepSeek 写作与图片 API 可以继续承担分析、原创写作和配图。

完整采集模式需要有效的 X 账号 `auth_token`，也需要可访问 X 的网络。它不是匿名采集器，也没有提供一个购买密钥就自动可用的数据服务。用户此前明确排除了登录个人 X 账号后采集的路径，本次研究没有改变该约束，没有读取浏览器会话、安装生产服务或发起凭据采集。

初始评估完成代码阅读、工具 Schema 核对和 60 个 Python 文件的语法检查。没有配置 X 登录凭据或 PostgreSQL，没有运行上游需要登录凭据的 Worker。下文的补充验证仅调用现有第三方公开接口，不把短期成功当作稳定性验收。

## 补充结论：与现有匿名来源结合

用户再次明确：不使用个人 X 账号登录采集，不提供 Cookie，不读取浏览器会话。推荐方案调整为在现有 Node + SQLite 工作台中适配匿名公开数据来源，吸收上游的研究、记录和分页设计；不需要以启用登录型 Scweet 为前提。

2026-10-08 21:52—21:53（北京时间），对现有公开服务进行了有界实测。请求只携带 Accept 和 User-Agent，没有 Cookie 或 Authorization，没有调用 AI 模型或修改工作台生产数据。

官方文档提供 `/2/conversation/{id}`，用于获取原帖、串文、其他用户回复及下一页游标。当前工作台原先仅使用 `/2/thread/{id}`，且只保留目标作者的续帖，两者不是同一种采集范围。

这证明在调用端不提供个人 X 凭据，也能获取真实可见评论样本。三次测试的第二页均失败，不能将第一页或空返回标为完整采集。平台显示的回复累计数与返回记录也未必使用相同统计口径，不能据此精确推算缺失条数。

匿名是指我们的调用端不携带用户登录会话，不代表上游服务内部完全没有账号。FxEmbed 的部署文档支持由服务部署方持有账号凭据；当前托管实例的具体凭据配置没有验证。我们不要求用户提供个人账号，也不承诺第三方接口永久稳定。

建议复用顺序：

1. 继续通过现有匿名来源读取帖子、长文、公开指标；补充独立评论接口。
2. 将评论与作者续帖分开保存，关联原帖、作者、发布日期、采集时间和回复关系。
3. 保存分页检查点与覆盖状态；第二页失败显示“已取得 N 条，续页失败”，保留第一页成果，后续能够重试。
4. 在现有 SQLite 中增加正文版本和指标快照，参考上游的幂等与变化判断；只有多次实际观测才能计算增长。
5. 复用上游研究卡片与相对高互动方法，由现有 DeepSeek 根据真实帖子和评论生成引用明确的研究与选题。

若以后直接复用整个上游后台，需要增加独立的匿名 Source，并同时修改 CollectionRequest 的必填 account_id、preflight、账号状态和 Skill 路由。不能伪造账号记录来绕过检查，也不能只设置一个“关闭登录”参数就宣称接入成功。

### 2026-10-08 匿名补全实现与验收

已在现有 Node + SQLite 工作台接入匿名评论补全。没有启用上游登录型 Worker，也没有创建持续监测或定时任务。

发现原评论入口的第二页返回 404，并不意味着公开搜索没有其他评论。新增 `/2/search`，用 `conversation_id` 关联原帖，按最新、热门、媒体和 UTC 日期分段补充，合并去重。缺父评论时单独读取父帖，确认回复链回到主帖后才进入可见素材，未确认记录单独保留。

| 同一原帖样本 | 初始单入口首页 | 优化后实际取得 | 验证方式 |
| --- | --- | --- | --- |
| 数字生命卡兹克 `2106762127159734314` | 33 | 127 | 工作台 API 采集、SQLite 保存与重新读取，127 个不同 ID |
| 宝玉 `2108072320317145306` | 35 | 58 | 工作台 API 采集、SQLite 保存与重新读取，58 个不同 ID |
| 鱼总聊 AI `2107841508598538567` | 5 | 5 | 独立运行相同采集器，各匿名路径合并后仍为 5 个 ID |

这些数字是指定帖子在测试时取得的记录，不是整个账号、所有评论的覆盖率，也不用于推算当前原帖计数与采集计数的差额。评论和互动持续变化，后续刷新可能增加。

每页落库，单轮最多 40 次请求、约 2 分钟；用保存的检查点继续，不设累计 40 次或固定评论总数上限。网络故障有一次有界重试；限流停止并保存暂停时间。连续空页结束当前路径；重复游标或重复结果页标为未推进，避免无限空翻。原评论入口失败不会阻止搜索补全。保留评论正文变化的最近 5 个旧版本和最近 10 次不同的指标快照；它们来自实际读取，不反推开始记录前的历史。

网页入口：X 信号源 → 打开帖子 → 评论素材 → 补全公开评论／继续补全评论。可按最新或高赞查看、分批展示、复制包含作者和原帖链接的素材。网页刷新重新打开后从 SQLite 读取。评论尚未自动加入 DeepSeek 的博主研究输入，不能声称已经执行了评论需求归纳。

43 项自动化测试通过，含匿名请求无凭据、翻页失败后的搜索补全、断点恢复、嵌套归属、去重、正文与指标历史、限流保存和界面转义。浏览器验收通过：按钮采集、进度显示、嵌套评论、排序、刷新保存结果、桌面和手机布局。

当前接口仍来自同一 FxEmbed 上游；增加多条读取路径是覆盖优化，不宣称为多个独立数据供应商。

依据：[公开搜索接口文档](https://docs.fxembed.com/api/twitter/operations/2search/)、[评论接口文档](https://docs.fxembed.com/api/twitter/operations/2conversationid/)、[服务方凭据说明](https://docs.fxembed.com/deployment/credentials/)。

## 实际架构与获取方式

| 部分 | 源码中的职责 | 对现有项目的意义 |
| --- | --- | --- |
| 中文 Skill | 推断参数、选择 MCP 工具、核对数据、引用材料并编写研究结论 | 可借鉴研究流程；复制文件不会自动给网页增加功能 |
| MCP 服务 | 35 个工具，提交和查询任务、账号引用、导出、档案与研究笔记 | 给 Codex 使用，或者由工作台后台作为 MCP 客户端访问 |
| Python Worker | 独立消费队列，采集、分页、检查点、限流退避与监测调度 | 持续记录需要 Worker 进程运行；关闭 Agent 不等于关闭 Worker |
| PostgreSQL | 帖子、评论、正文版本、快照、档案、队列与任务结果 | 与现有 Node + SQLite 不同，需要服务连接与数据适配 |
| Scweet | 使用账号 Cookie 访问 X 网页内部 GraphQL，解析响应 | 没有走官方开发者 API，但实际使用了登录会话 |
| Markdown 知识库 | 帖子分析、每日清单、素材卡、需求卡、资源卡、发布组合和决策报告 | 可映射到工作台的素材与研究面板，并保留出处 |

采集入口在 `mcp/scweet_mcp/source.py`：时间线用 `profile_timeline_with_replies`，评论用 `tweet_detail`，指标更新用 `tweet_lookup`。账号、分页和网络请求由后台处理，不由语言模型凭空生成。

`auth_token` 是 X 网页登录 Cookie，不是 DeepSeek Key、图片 Key、官方开发者 Bearer Token 或 MCP 服务访问令牌。凭据应由采集端持有，前端、报告和大模型只使用账号引用与公开材料。

## 值得优先吸收的能力

### 评论区需求研究

当前工作台的串文读取只保留目标作者的续帖，不等于收集其他读者的评论。上游支持直接回复和整段会话、分页分支、断点继续与覆盖状态。

建议在博主研究中增加“评论需求”：按问题、使用障碍、求教程、价格疑问、效果质疑等维度由 DeepSeek 归纳；每条需求附原始评论、链接、所在帖子和样本数量。归纳类别是我们的适配建议，并非上游已实现的固定语义分类。

上游 `reports.py` 提供发布时段、文字长度、关键词和词典情感等统计。其评论关键词不是用户意图标签，真正的需求与风格解释由宿主 Agent 完成。接到网页时，需要把已有写作模型接入此解释步骤。

### 相对高互动素材

`research.py` 使用样本中位数作为基线。默认高互动候选门槛为 `max(10, 样本指标中位数 × 2)`，默认指标为点赞。比较文字长度、问句、链接和媒体等特征，并输出源帖证据。

这比仅按总曝光排列更适合研究同一个博主的异常表现。它仍不能证明某个写法导致传播，也不是低粉爆款的完整判定：还需核实粉丝数据、普通内容基线、样本范围和帖子发布时长。

### 变化与增长历史

上游保存正文版本和多次指标快照，支持查询正文变化和观察期间的互动增量。一次指标记录不能判断增长；开始记录前的传播曲线不能从当前累计量反推。

监测默认每小时发现新帖，每轮核查最多 5 篇已存帖子；默认不持续采评论或生成 AI 日报。需要明确开启监测并保持 Worker 与数据库运行。电脑停机期间没有连续观察记录。

### 研究资料复用

最新版本已加入本地 Markdown 知识库和 4 个笔记工具。按博主、日期、主题及类型检索，正文素材、评论需求、资源和发布组合通过稳定 ID 关联，支持更新冲突检查与版本保留。

可将选中的发布组合送入现有“爆款创作”，使用自己的事实、角度和例子生成原创稿，再调用已配置的图片服务。

## 0.002 元的判断

本次检索源码和文档，没有找到 0.002 元的定价、支付渠道、按次扣费实现或供应商报价。该数额来自用户提供的项目介绍，尚未核验。

一次研究任务不是一次网络请求：可能包括账号检查、身份解析、时间线多页、评论多页、指标更新和请求初始化。当前适配器每次页面读取还会调用 `probe_token`；上游明确说明跨任务 30 分钟验证缓存尚未实现。实际网络量必须测量。

总成本应分别记录账号／数据服务费用（如适用）、网络与运行资源、AI 分析写作、图片生成。若外部供应商确实按每次请求 0.002 元收费，则 1,000 次请求算术上为 2 元，但这不是该项目提供的价格承诺，也不是 1,000 次完整博主研究的总费用。

## 建议接入方案

### 方案 A：研究方法与笔记先落地

在仍使用现有匿名公开来源或手动导入数据的前提下，吸收评论证据、相对基线、研究卡片、版本与快照的设计。匿名评论补全已在工作台落地，通过搜索分页补上原评论入口续页失败的缺口，保留每条路径的读取记录。来源没有提供的记录仍不虚构。

这种方式适用于保持现有账号约束的情况。可以先改善研究质量与材料复用，采集能力仍受当前来源限制。

### 方案 B：独立采集服务作为可选信号源

如以后具备用户明确授权使用的采集凭据，保留上游 Python + PostgreSQL，使用固定版本部署为独立服务。现有 Node 后台通过 MCP 调用，或经小型桥接 API 提交任务、查询进度和取回结果，再转换成工作台自己的帖子与评论格式。

这比把整个 Python 后台改写为 Node、把所有 PostgreSQL 逻辑迁入 SQLite更容易保留上游升级能力。桥接 API 是需要开发的适配层，不是目前已经存在的普通 REST 接口。

现有匿名来源继续可选。不同来源分别保留采集时间、原始格式、完整性和错误原因，不能把两个来源拼接后宣称全部帖子已取得。

MCP 接到 Codex 后可以在对话中使用；网页要生效，还必须增加后端调用、状态转换、数据入库和相应 UI。

### 方案 C：跨电脑共用同一个服务

当需要多设备复用账号观察名单、评论和监测历史时，将采集服务与研究数据库集中运行，两台工作台查询同一服务。使用加密连接与服务访问令牌，原始 X 登录凭据留在采集端。

这是后续部署方案。仅通过 Git 下载代码仍不会同步私人数据或保证新电脑网络可用；新项目不能自动修复之前另一台设备的刷新失败。

## 必须验证的适配点

- 字段：当前工作台使用 FxEmbed 格式，上游使用 `TweetRecord`。作者 ID、帖子 ID、日期、原文、引用、回复关系、媒体、指标和完整性需显式映射。
- 收藏：底层 `TweetRecord` 有 `bookmarks`，但上游统一增长统计只处理点赞、评论、转发、曝光和引用。保留收藏值，并按需要扩展快照统计；未知不能补零。
- 长文：解析器支持 `note_tweet` 的长帖文字。X Articles 的完整正文、封面、引用长文和置顶需单独用真实样本验证，不能用功能开关存在证明已读到全文。
- 中文评论：用真实中文样本检验问题归纳，不把双字词频或简单情感词典当作需求结论。
- 账号：没有凭据、失效、需验证、限流、网络不通、Worker 未运行和无匹配数据分别显示。不得让空白页面掩盖失败。
- 发布时长：比较同龄帖子表现；已有累计量不能视为刚刚新增流量。
- 恢复：确认 Worker 重启后检查点可继续、重复任务不重复计数、已采数据仍保留。
- 持续监测：由用户明确开启，显示范围、频率、运行状态和记录空档；不把后台启用当作 AI 自动分析已执行。

## 原版登录型服务的候选验收（不是当前推荐采集路径）

满足采集凭据前提后，选择 3 位已有对标作者，例如鱼总、逸尘、数字生命卡兹克；先做最近 7 天、有界条数的单次采集，每位挑 2—3 篇采可见评论。记录实际请求量、耗时、失败类型和覆盖率，核对主帖、长文、收藏和评论来源。

确认数据正确后，再由用户明确开启一位作者的 48 小时观察，用至少两次快照验证增长、正文版本和断点恢复。验收成功后再扩到更多账号。该段是推荐的未来验收，当前没有运行这轮采集或创建定时监测。
